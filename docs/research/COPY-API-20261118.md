## 1. 用户原话与本轮目标

> 关于拷贝漫画它是不是有这种好多这种什么C10这种编号这种什么什么画集啊，是不是也有专门的接口啊？我希望你去研究一下，以及拷贝漫画的接口，我觉得应该不只是我们现在这个功能吧。可以都试着把它们全部接入，丰富一下我们的功能，请你深度的调查研究一下。如果需要什么我可以提供给你，比如说拷贝的安装包啊或什么

本轮把这个需求拆成三件可交付的事情：说明截图中 C103 的真实含义；把当前项目与已找到的拷贝接口逐项对照；先实现合同清楚、能沿用现有身份与页面结构的功能，再把仍需客户端证据的部分明确留在清单中。接口清单是此次调查的覆盖范围，不是官方完整 API 规范。

## 2. C103、画集、题材与专题分别是什么

| 概念 | 已有证据支持的含义 | 对产品的影响 |
|---|---|---|
| C103 | Comic Market 103 的届次。官方活动说明对应 2023 年 12 月 30—31 日。[P1] | 适合在分类中呈现为“展会”，不能当作作品编号或任意年份参数。 |
| 拷贝里的 C95—C108 | 公开分类页与 Neo 固定源码中的 theme 标签；实际请求依赖返回的 `path_word`。[P2] [N8] | 可以与其他真实分类共用 `/comics?theme=…`，无需另造一套 C103 详情接口。 |
| 画集 | 内容形式；此次证据没有建立“所有 C103 都是画集”的对应关系，也没有证实一个独立画集接口或可靠枚举。 | 只展示服务端明确提供的类型文字，不凭标题、展会届次或数字枚举自行归类。 |
| 原作／社团／类型 | 详情 DTO 中分别存在 `parodies`、`clubs`、`reclass.display`。[N9] [N10] [N11] | 原作可在有合法 path 时进入关联作品目录；没有 path 的原作、社团与类型先按真实文字展示。 |
| 专题 | 站方编辑组织的独立内容集合，公开页面与 `/topics`、`/topic/{path}`、`/contents` 对应。[P4] [N1] [K1] | 可以做专题目录、说明与作品列表；专题与普通题材筛选应保留不同身份。 |

截图里出现 C103，说明它可以携带一个展会标签；这本身不证明作品形式、适龄属性、出版年份或版权类型。普通与成人区继续沿项目既有 profile 隔离，展会标签不能改变来源身份、书架归属或阅读记录归属。

本次读到的 C103 分类 path 有 `comiket103`，C98 则明确使用大写 `C98`。这些值应当视为来源提供的标识，不可用“届次数字转小写 slug”的规则批量生成。[N8] [P3]

## 4. MangaFlow 原有覆盖与本轮补齐

### 4.1 基线里已经存在的能力

基线已经包含作品／作者搜索、单题材与作者目录、详情、分组章节、阅读、推荐、四个榜期及男女频、最近更新、作品评论／回复／章评，以及独立账号登录、收藏、云端历史和真实阅读后的章节状态同步。这些都不应重新算成本轮新增。[M1] [M2] [M6]

旧标签入口的主要缺口是：全局初始目录来自静态 `CopySearchTags`，届次停在 C95—C101；详情已经能解析真实 `theme` 的名称和 path，点击已加载详情里的 C103 并不需要专用新接口。因此“详情可点，但初次进入标签搜索找不到 C103”可以由目录覆盖不足解释，不能推导成服务端没有 C103。[M1] [M3] [M4] [M7]

### 4.2 本轮首批源码

| 新增部分 | 具体落点 | 结果与边界 |
|---|---|---|
| 完整题材／展会字典 | `themeDirectory()` | 读取真实名称、path 与可选数量，按服务端总量继续分页；初始 `limit=500` 不是目录上限。 |
| 原生筛选选项 | `filterDirectory()` | 读取 `theme`、`top`、`ordering`，不硬凑未经证实的地区与连载状态组合。 |
| 原生目录 | `browseCatalog(selection, page)` | 统一承接 theme、top、ordering、parody；保持来源顺序及条件所属状态。 |
| 专题目录 | `topics(page)` | 漫画专题 `type=1` 分页读取。 |
| 专题说明 | `topic(path)` | 读取标题、简介等真实字段；不把年份标题解读为通用年份筛选。 |
| 专题作品 | `topicContents(topic, page)` | 读取直接作品列表；排除无效或其他类型后仍按原始页范围推进游标。 |
| 汉化组搜索 | `SearchTarget.TRANSLATION_GROUP` | 使用已证实的 `q_type=local`，移动与桌面入口同步补图标、名称和提示。 |
| 详情元数据 | `Manga.originals / clubs / contentType` | 解析并保留原作、社团、真实类型文字；有合法非空 path 的原作才可跳转。 |
| 界面与状态 | 动态标签、展会分组、目录／专题 `CopyExploreController` 与 UI | 查询身份包含筛选与原作／专题；分页、错误与切换后的响应归属分离，避免旧请求覆盖新页面。 |
| 本地记录兼容 | 共用漫画 JSON 编解码 | 新字段可保存，旧记录默认空；不改变来源和作品身份。 |

六个方法是六种新增读取操作，不是六个全新后端系统。比如原作与题材目录都建立在 `/comics` 上。合并最新主分支时保留了普通／成人搜索隔离与原生作者、标签搜索；汉化组入口仅在普通分区显示，目标只路由到已启用的拷贝来源，查询缓存包含当前来源配置。所有新增项目前均为**源码已实现并整合、运行待确认**，尚不能据此承诺安装后的界面效果、服务可达性或完整运行稳定性。

## 6. 最容易实现错的语义

### 6.1 App 的 top，不等于网页 region＋status

上游 App 请求把 `korea`、`west`、`finish` 等放在同一个 `top` 参数里。这里同时混入地区与完成状态，因此目前没有证据支持任意“地区 × 完结状态”的自由组合。Kira 注释认为 `top=japan` 可能表现为无筛选，这只能列为作者观察，不能当成本轮服务端事实。[N1] [K1]

公开网页的实际 C98 链接带有 `status=1`，说明网页链接层与 App 参数层存在不同。此次归档没有足够的 `region` 精确值与 App 对应关系，因此不照搬网页 `region/status` 到 v3，也不从一个 `status=1` 链接推导全套状态枚举。后续若拿到网页或 APK 的真实组合请求，应分别记录再建立转换。[P3]

### 6.2 path 大小写与多标签交集

名称用于显示，path 用于请求和身份。C98 的 `C98` 与其他 `comiket…` 不能按统一命名规则生成；可选数量也只能表示该次来源返回，不应把内置历史计数显示成实时数量。[N8] [P3]

既有多标签功能读取一个源结果流，再补全详情标签做客户端交集；源码有限制每次加载的源页数与详情并发。它可能暂时筛出空页，但这不能证明全库不存在交集作品。它还不能当作已验证的服务端 AND 搜索。[M1] [M4]

### 6.3 响应嵌套与分页不能混用

推荐和许多排行条目在 `list[].comic` 内；`/comics` 与专题 contents 是直接作品。首页聚合更复杂：`recComics/rank*` 是带 list 的嵌套条目，`hotComics/newComics` 可为裸数组，`finishComics` 是直接作品列表，专题又是另外的 DTO。把它们全塞进一个“尽量猜字段”的解析器会掩盖缺内容和游标错误。[K1] [N3]

专题限定漫画类型 `type=1`。若响应里有其他类型、缺少漫画对象或无效行，展示层可以跳过，但下一页仍应按服务端 offset、limit 与原始行数推进，不能按“本页显示了几张卡片”计算。服务端明确声明其他类型时不能强行按漫画打开。[K1] [N1]

### 6.4 年度专题不等于完整榜单或通用年份过滤

公开专题页里有年度奖项与季节动画相关集合，但专题标题中的年份、period、创建时间分别有各自语义，不能凭它们发明 `year`／`season` 筛选参数。2026 年相关专题公开说明其收录的是可提供的翻译作品，并有未收录条目，因此应称“来源专题”，不能承诺完整官方获奖榜。[P4] [P5]

### 6.5 当前轮播已经按日期轮换

基线 `DiscoverScreen` 已按本地日期从真实推荐池取六项，源码不是“始终固定前六个”。但池子来自 `/recs?pos=3200102`，并不是完整官方首页 banner/feed，日期换一组也不等于上游有新推荐。[M5] [M2]

基线刷新会从第一页重新读已加载范围，成功后整体替换，失败保留旧内容；缓存有不同的时效策略。没有当前设备、真实响应和安装版本，不能把用户见到“内容长期不变”直接归因于单一缓存 bug、轮播不轮换或拷贝不更新。[M4] [M8]

## 7. 本轮源码如何接入，以及还没有做到什么

首批能力沿现有 MangaFlow 组件接入：标签选择器把真实 Cxx 归入“展会”，按届次降序；普通题材保留原交互。详情在既有信息区域渐进显示原作、社团、类型，有合法原作 path 才提供跳转；汉化组搜索在移动与桌面保留相同含义。目录和专题用独立查询状态保存筛选、页码、内容、错误与请求归属，不让旧统一搜索的热度重排覆盖原生排序。

| 源码组 | 主要文件 | 交付边界 |
|---|---|---|
| 接口与模型 | `CopyMangaRepository.kt`、`CopyBrowseModels.kt`、`Models.kt`、`SearchTags.kt` | 六个只读方法、汉化组搜索、真实元数据与默认分类补充 |
| 状态和接线 | `CopyExploreController.kt`、`MangaViewModel.kt`、`MangaFlowApp.kt` | 动态目录、条件状态、详情原作到目录、来源切换归属 |

以上文件名单描述本轮覆盖层；最终以集成提交的真实 diff 为准。没有本轮最终 SHA 或 CI 结果时，本报告不把源代码准备写成发布完成。

有了更多接口也应按完整产品链路分批完成：先让分类、专题与原作找到内容；再接官方首页与榜单变化；账号写入沿既有个人会话处理；下载和小说分别解决额度与阅读模型。这个顺序是基于现有架构和已知合同的工程判断，不是对未实现能力的完成承诺。
